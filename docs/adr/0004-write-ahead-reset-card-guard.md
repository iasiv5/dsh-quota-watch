# Protect uncertain reset-card redemption with a write-ahead host guard

A reset-card POST may irreversibly consume a card, while a timeout or process crash after sending it cannot prove whether the provider did so. Before every manual or automatic redemption, the host atomically records a minimal pending attempt without credentials and refuses to send the POST if that record cannot be saved. A conclusively settled attempt clears the record only after the clear succeeds; an uncertain outcome or restart keeps both card types blocked, disables both automatic-use authorizations, and requires explicit user reconciliation against the provider's card count and quota before a double-confirmed acknowledgement can unlock spending. Acknowledgement never re-enables automatic use or spends a card.

This deliberately trades availability on a storage failure for a durable safety boundary: an in-memory warning, a lock over only the original card type, or recording the failure after the POST leaves a crash or overlapping-weekly-card path to another irreversible redemption. Ordinary success, awaiting a card, and recoverable probe failures do not need a permanent event ledger; only an unresolved attempt is durable.
